# 0.2 版本后的后续迭代建议

> 基于 0.1.0 → 0.2.0 这轮（46 轮协作、主题/图标大版本）的全程观察，写给 0.3 版本迭代参考。
> 分「该补的 / 该收的 / 该防的」三块，按价值排序。

## 一、该补的：三个功能缺口（按价值排序）

### 1. 截止时间（deadline）——清单工具的"刚需之首" ⭐ 最推荐先做

现在的任务是「名称 + 状态 + 图片 + 备注」，没有时间维度。团队协同里"这个什么时候要"是出现频率最高的对话。

- **形态**：任务可选的「截止日期」字段 + 逾期视觉（红/警示）+ 按日期排序
- **工作量**：小——数据加字段 + 排序维度 + 日期选择器（Element Plus 自带 el-date-picker）
- **与现有体系的融合**：天然融入倒序排序、状态分组；逾期任务可与"待修复"状态联动强调
- **价值**：每个团队都需要，感知价值极大

### 2. 负责人（assignee）——多人协同的语义核心

现在备注能区分"谁写的"，但任务本身不知道"谁负责"。

- **形态**：任务「负责人」下拉（从在线/历史成员里选，复用 clientId + 显示名体系）
- **价值**：一列回答"这事归谁"——从"共享清单"走向"协同工具"的分水岭
- **注意**：与身份体系（clientId + 显示名）天然兼容，无需账号系统

### 3. 看板视图（按状态分三列）

已有完美的三态 + 状态变更动画，看板只是同一份数据换个摆法。

- **形态**：列表/看板切换视图；看板 = 待修复/修复中/已完成三列 + 拖拽换状态（复用现有 onStatusChange + FLIP 动画）
- **工作量**：中等（前端）
- **价值**：进度一眼可见，对管理者是另一个维度的价值

> **如果三个只做一个：做截止时间**——与现有排序/状态体系融合最顺，每个团队都需要。

## 二、该收的：克制边界（别丢定位）

核心差异化 = **局域网 + 数据自持 + 零成本上手**。守住：

- ❌ **不做账号体系/权限系统**——局域网信任模型不需要，做了就重了
- ❌ **不做云端同步**——除非明确需要远程访问；那时优先 Tailscale/内网穿透（借用网络层），不自己搭服务
- ⚠️ **功能优先级自检**：问一句"这个功能让同事第一次用就懂吗"——不懂就缓

## 三、该防的：工程与分发

### 1. 分发升级链路

现在发 exe 给同事，但 0.2.0 怎么通知他们更新？

- 轻量方案：底部版本号旁加「有新版本」提示（服务端版本对比，无需更新器）
- 或至少固定「更新说明」习惯（每次发版附一页：改了什么 / 数据是否需要迁移）

### 2. 代码签名（SmartScreen）

打包日志"signing is skipped"——同事双击 exe 会弹「未知发布者」警告，首次体验打折。个人代码签名证书（一年几百元）值得考虑。

### 3. 大列表性能

- 包体积：73 文件 327MB（node_modules 未瘦身），首启解压偏重——可评估裁剪依赖
- 渲染：行列表是手动 DOM + FLIP，任务上千条时要提前摸底（确认无性能悬崖）

### 4. 视觉类问题的验证方式（协作效率杠杆）

0.2 这轮查看器闪烁来回 5-6 轮，本质是"视觉问题只能真机看"。

- 建议：动效/视觉改动，工程师先自建**最小可验证样例**（独立 HTML，内嵌关键 CSS/JS），一次到位，减少真机来回轮次
- 对需求方：视觉问题尽量给"现象描述 + 操作步骤 + 期望效果"三要素，方便快速复现

## 四、产品层面的真心话

0.2 最大的成功不是功能，是**「名字与质感匹配」这个共识**——星空要有星空、纸面要有纸纹、抽象要有设计感。它让工具从"工具"变成"有性格的工具"。

**性格是局域网小工具的护城河**：大厂产品做不到为 5 个人的团队长成这样。建议 0.3 及以后，所有大功能先过这个审美关（名字 → 质感 → 细节），再谈功能。

> 需求方原话（0.3 方向）："后续这些很小的点，可能才是我真正的产品亮点。"——体验小点优先于功能大点，与本文建议一致。
